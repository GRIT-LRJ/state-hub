# 新手术语表：平台 / Runtime / 驱动 / 状态机

> 本文档用"硬件思维"解释软件开发概念（作者原为硬件背景）。
> 术语以本平台（state-hub）上下文为准。

---

## 1. 驱动（Driver）

### 硬件世界的驱动

操作系统只认识"统一接口"（例如"鼠标移动了？""显示一个圆"），不认识具体芯片。
**驱动 = 把统一接口翻译成具体设备指令的那层软件。**
让"不同的硬件在系统眼里长得一样"。

### 本平台的驱动

沿用同样的思想，只是宿主从操作系统变成我们的平台：

> **驱动 = 可插拔插件（JSON 声明 + 实现代码），把平台的"统一状态"翻译成某个具体输出设备的动作。**

示例（同一个入口 `apply(state)`）：

| 驱动 | 平台说"decision"时做什么 |
|---|---|
| 虚拟驱动 | 前端画一个琥珀色块（调试用） |
| VK87 键盘驱动 | 写 65 字节 HID 报告 → 键盘灯变琥珀色 |
| PushPlus 驱动 | 发 HTTP 请求 → 微信推送"⚠️ 需要你回答" |
| 未来网络设备驱动 | 调用该设备的 API |

要点：

- **不限于硬件**：微信推送、网络设备、日志都可以是"驱动"（即"输出通道/反应器"）。
- **不是内核驱动**：不装进 Windows 设备管理器，只是应用级插件。
- 也可叫 **适配器 / 执行器 / 输出通道**，概念相同。

---

## 2. 平台（Platform）

**平台 = 被很多人"搭在上面"的那一层**，提供公共能力与接口，自身不解决具体设备问题。

本平台（state-hub）包含：

- 事件 API：应用上报状态（`POST /api/events`）
- 状态机：把多个应用状态仲裁成"当前唯一状态"
- 驱动注册表：知道有哪些驱动、各自支持什么
- Runtime：驱动管理宿主（见下）
- 前端：驱动管理、状态映射设计、状态机可视化、测试台

类比：Android = 平台；App = 应用（Codex/DSH）；设备驱动层 = 让 App 用上硬件的部分。

---

## 3. Runtime（运行时）

### 软件通用含义

让代码跑起来的环境，如 Node.js / .NET / JVM：
提供进程、内存、事件循环、模块加载等底座。

### 本平台的含义

**Runtime = 平台内部专门"管理驱动"的宿主（插槽管理器）**：

- 发现驱动（JSON + 代码）
- 用 JSON Schema 校验声明
- 加载驱动实现，管理生命周期
  - `init()`：连接/初始化
  - `apply(state)`：响应某个状态
  - `status()`：查询是否在线
  - `dispose()`：释放/断开
- 把状态机的结果广播给所有驱动

以后想隔离驱动崩溃：改 Runtime 为"独立进程 + 消息通信"，**Driver 接口不变**。

---

## 4. 状态机（State Machine）

**状态机 = 判定"现在整体处于什么状态"的规则引擎。**

- 应用上报的是各自状态（Codex 完成、DSH 等待回答…）
- 状态机把这些**仲裁**成一个（灯/推送只能表达一个状态）
- v1 固定状态：`completed` / `decision` / `none`
- 仲裁优先级草案：**decision > completed > none**
- 无任何活动 → `none`（驱动执行默认/恢复）

---

## 5. 一句话关系图

```
应用        = 乘客（Codex / DSH）
平台        = 车站（统一调度）
Runtime     = 车站的调度系统（管每一条线路/车辆）
驱动        = 车辆（把"要去哪"变成"具体怎么走"：键盘灯 / 微信 / 网络）
状态机      = 调度规则（哪条线路现在该发车）
```

---

## 6. 与现有 Codex 实现的关系

现有 `codex-keyboard-light.exe` 只是"Codex 事件 → VK87 灯带"的**直连实现**，
内部其实已经隐含了：状态语义、会话聚合/仲裁、HID 驱动、协议报告，
但全部耦合在一起、只认一个设备。

平台化 = 把这四层拆开：
应用只上报 → 平台状态机仲裁 → Runtime 广播 → 各驱动自己翻译执行。
